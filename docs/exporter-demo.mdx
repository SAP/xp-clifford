## Step 1 — BTP Cockpit: Examine existing landscape

[Open BTP Cockpit](https://canary.cockpit.btp.int.sap/cockpit#/globalaccount/8b7fcd40-9784-4c4c-bcd6-f1a7c7ce9566/subaccount/f9f210e6-e263-4880-8073-c530d971752c/subaccountoverview) and walk through the existing landscape:

- Global account with subaccounts already provisioned
- Each subaccount has entitlements assigned, service instances running, CF environments enabled

This is an existing BTP landscape — not something we're creating from scratch. **How do we bring this under Crossplane management?**

---

## Step 2 — `btp-exporter`: Export the landscape as Crossplane resources

The first step is to express what already exists as Crossplane resource manifests. Once we have those, Crossplane can start observing and eventually managing the landscape.

The **BTP Exporter** is built exactly for this — it connects to BTP, reads the existing resources, and writes them out as Crossplane YAML.

### Log in with the BTP CLI

The exporter reuses an existing BTP CLI session, so we authenticate first:

```bash
btp login --sso
```

This opens a browser tab for single sign-on. Once authenticated, make sure the session is targeting the **global account** — not a subaccount:

```bash
btp target --global-account <your-global-account-subdomain>
```

You should see the global account as the current target.

### Run the exporter

The exporter reads the BTP CLI session and exports all resources from a subaccount as Crossplane manifests:

```bash
./btp-exporter export --all \
  --resolve-references \
  --output ./my-landscape.yaml
```

> `--resolve-references` automatically expresses resource references by Crossplane resource names, not GUIDs.

The tool writes a multi-document YAML file — one Crossplane resource per `---` block. Subaccounts, entitlements, service instances, service bindings, CF environments — all described exactly as they exist in BTP today.

---

### Examine the YAML

Validate the exported file contains the following resource kinds and resource references are by name, not by GUIDs:

- **Subaccount** — the subaccount itself
- **Entitlement** — 3 entitlements assigned to the subaccount, excluding auto-assigned entitlements
- **ServiceManager** and **CloudManagement** — internally ServiceInstances, but exported as dedicated concrete types because the provider treats them specially
- **ServiceInstance** — all other (generic) service instances
- **ServiceBinding** — bindings for the service instances
- **CloudFoundryEnvironment** — the CF environment enabled on the subaccount

We now verify if the exported resources are correct and can be observed by Crossplane. The next step is to apply the manifests to a cluster with the BTP provider installed and a ProviderConfig pointing at the right global account. Make sure that `managementPolicies` are set to `Observe` only, so that Crossplane does not attempt to create or delete any resources — it will simply look up each resource by its BTP GUID (annotated as `crossplane.io/external-name`) and reconcile it to `READY=True`.

---

## Step 3 — `kubectl`: Apply to a cluster and observe all resources to be `READY=True` and `SYNCED=True`

With the BTP Crossplane provider installed and a ProviderConfig pointing at the right global account, apply the exported manifests:

```bash
kubectl apply -f my-landscape.yaml
```

Then check that everything comes up observed:

```bash
watch -d kubectl get managed
```

Once all resources show `READY=True` and `SYNCED=True` (can take a few minutes), the landscape is under Crossplane management. From here you can tighten the `managementPolicies` to let Crossplane actively reconcile, create, or delete resources.

To clone the landscape, duplicate the Subaccount resource, give it a new name, and remove the `crossplane.io/external-name` annotation. Crossplane will provision a new subaccount in BTP — fully described in code, no clicking required.
